PX-42F UI Guidelines

How every settings screen looks and answers the keys. Apps get the same screens (the ui_*() calls of px_app.h), so they follow the same rules.

1. The four rules

  1. Only standard elements. Every setting is set with one of the screens in section 3: a radio list, a check box, a pull-down, a number, a time, a date, text, a list, a form, an icon page or a message. No screen invents its own way.
  2. Tabs have fixed places. F1 is what ENTER does, F4 and F5 are the arrows (▲ ▼ in lists, ← → on icons), F6 is EXIT. The same thing is always under the same key.
  3. Only live tabs show. A tab that does nothing on this screen isn't drawn, and its place stays empty: the others don't move into it.
  4. EXIT never changes anything. It goes back, or leaves an editor as it was. The EXIT tab and the EXIT key do the same.

2. The screen

  • Title bar (13 px, black): the screen's name at the left, the time at the right, the shift sign while SHIFT is down. The name is the one on the row or icon that opened it.
  • Rows: up to 7, in the small font, 13 px apart. The picked row is black. A scroll bar at the right edge shows where the rows are when there are more than 7.
  • Tabs: six, one over each key of the top row (Σ+ to XEQ), called F1 to F6 here.

Icons with SHIFT on, on home and in Apps and Games: FAV in a folder, UNFAV on a home favourite, blank where neither applies; MOVE not on Off. On an icon with neither, SHIFT changes nothing. BACK here only ends SHIFT: the plain tabs come back. The pages inside keep their tabs.

  • F1 names what ENTER does: ENTER where ENTER opens, takes or answers (never OK), or a verb where it does one thing (SAVE, LOAD, USE, IMPRT).
  • F2, F3: other actions on the picked row (EDIT, DEL, RENAM, MOVE, FAV).
  • F4, F5: the arrows. In lists and forms ▲ ▼, only when there is more than one row; they put them there by themselves when the places are free. On icons ← →, always.
  • F6: EXIT, on every screen that can be left. Lists and forms add it by themselves.
  • A list with four actions (States: SAVE LOAD RENAM DEL; Programs: IMPRT EXPRT RENAM DEL) uses F1–F4 and has no ▲ ▼ tabs: the arrow keys still move.
  • A screen that only tells something has just ENTER (EXIT answers it too).

What shows

  • Only the tabs that do something now. A list of states with none saved shows SAVE and EXIT; Alarms with none shows NEW and EXIT.
  • A hidden tab leaves its place empty. Its key does nothing (no beep, no other action).

6. When a change counts

  • One value (radio list, number, time, date, text): on ENTER or F1. EXIT leaves it as it was.
  • Settings form and check boxes: each change at once, as it's made. EXIT leaves the page; nothing to undo.
  • Record form (an alarm): nothing until SAVE; EXIT drops every change. SAVE refuses what can't work (a time already past) and says why.
  • Preview (fonts, splash images): picking one from the pull-down shows it; only USE takes it, and EXIT puts the pull-down back on the one in use.
  • Settings changed often from programs are written to flash at OFF, not at once (settings_save_later()).

7. Lists

  • A setting's current value is at the right of its row.
  • A radio list's filled button is always the value in use.
  • A list opened again comes back on the same row.
  • An empty list says so in one line, with what to do: "No saved states yet.", "No alarms. NEW sets one."
  • A list of files (states, programs, fonts, images) is read again each time it shows, so files copied in with USB Drive appear.

8. Questions and answers

  • Destroying something (delete, load over the memory, replace a file, format) asks first: F1 names the act, F6 is EXIT. Format Drive asks twice; nothing else does.
  • A result is one short line: "Saved X", "Could not save X", "Imported 3 programs". A failure beeps and says why.
  • Work that takes a while shows a line first: "Saving...", "Loading...".
  • Titles are in title case and name what was opened. Lines are short sentences, at most 31 characters. The same thing always has the same word (Delete, not Remove or Erase; Format erases the whole drive).

9. How it's checked

The screenshot tool (tools/menu_shots/run.sh) and the host tests (tests/run.sh) build the toolkit with UI_CHECK_TABS: every tab drawn is checked against the words of section 4, ▲ ▼ only on F4 F5, EXIT only on F6. A screen that breaks them stops the run with its word and place. The firmware doesn't carry the check.

In code: ui.c places ▲ ▼ and EXIT in lists and forms; settings_menu.c's CONFIRM(verb) makes a question's tabs, run_list() a list's, choose() a radio list's.

10. Apps

An app that uses ui_list(), ui_form(), ui_message() and the editors gets the same places and keys; a screen of its own gets the same title bar and tabs from ui_title() and ui_tabs(). The icon pages are the settings menu's alone. Leaving an app asks first, with the dialog "Quit NAME?" (QUIT / STAY): the firmware asks it when EXIT ends the app; an app that takes EXIT as a key asks it itself where EXIT would leave it. The game's pause and game-over messages are dialogs too (GO ON / QUIT, AGAIN / QUIT). Its own words for F1–F3 are its own choice, but F4 F5 stay ▲ ▼ and F6 stays EXIT.
